## §1 总目标（一句话）

把 design token 从「限期作废、只能靠再评审重铸」改成「**授权与时限解耦**」——
只要被评审的设计文档集没有变，就应当续期而不是重评审；文档变了才必须重评。

---

## §2 问题陈述

### §2.1 现象（用户实测）

会话跨度超过 1 小时后，已通过的设计令牌过期；而令牌**只能由一次新的设计评审重新铸造**，
于是每次都要重跑一整轮设计评审。批 1（D-29）让 TTL 可配，缓解了频率，但**没有解决机制**：
只要「重铸必须重评审」这条在，任何 TTL 到期都还要再评一次。

### §2.2 根因（已回代码核实）

| # | 事实 | 证据 |
|---|---|---|
| 1 | 默认 TTL 1 小时，与「设计→确认→实现→修复轮」的真实跨度不匹配 | `lib/advisor.mjs:200 TOKEN_TTL_DEFAULT_MS = 3600*1000` |
| 2 | 重铸只发生在新一次设计评审内 | `lib/advisor.mjs:1386-1388`（`pendingDesignToken` 缺失/失效 → 在评审入口重铸） |
| 3 | 过期后唯一指引是「重跑评审」 | `lib/eng.mjs:372`（`re-run the design review to mint a fresh token`） |
| 4 | 密钥升级会在启动时一次性作废全部在途 token | `lib/advisor.mjs:210-212`（D-25 自己写明的预期代价） |
| 5 | 上游 thincoder 的 TTL 是 7 天，且其 token 是**裸 `uuid:expiresAt`**（无签名） | `thincoder/src/agent-tools/design-token.mjs:34` / `:42-43`（"FLOW credential: uuid:expiresAt, exact slot match + TTL only"） |

### §2.3 为什么 HMAC 不是本题该保的东西（威胁模型，会诊判定 + 父侧核实）

| 论点 | 证据 |
|---|---|
| 该门禁**刻意 fail-open**：门禁自身异常即放行 → 它是纪律护栏，不是安全边界 | `lib/eng.mjs:167`（注释原话「门禁 bug 不能瘫痪整个会话」） |
| 真正挡住伪造的是**记录全等匹配**，签名在其后 | `lib/eng.mjs:366`（`token !== state.designToken` 判定在签名校验之前） |
| 密钥与 token 镜像**同目录**，能写后者者几乎必然能读前者 | `$DSH_HOME/.thincoder/{token-secret, design-tokens.json}`（`advisor.mjs:221-223` / `token-store.mjs:27-28`）；`chmod 0600` 在 Windows 上近似 no-op |
| 门禁只覆盖 `write`/`edit`，间接写不受管辖 | `lib/eng.mjs:38-39`（注释「间接写靠流程纪律」） |
| 净效果为负：密钥链带来启动全量作废 + 一条独立运维失效轴，换来防伪造增量 ≈ 0 | 见 §2.1 与 §2.2#4 |
| 上游独立得出同判并已删除（裁决自 2026-09-06 存活至今） | `thincoder/.../design-token.mjs:42-43` |

**结论**：删除 token 签名腿与整条密钥解析链。**但审批码不能一起删**——密钥同时是审批码的派生源
（`lib/advisor.mjs:709-710`，`designApprovalCode` 用 `createHmac(secret, token)`），
直接删会让 R2 的 `[APPROVE:<code>]` 防伪造语义静默归零。故审批码改为**无状态派生**（见 FR-T3）。

### §2.4 会诊发现的两个范围缺口（父侧已实证，必须纳入）

| # | 缺口 | 证据（已读码核实） |
|---|---|---|
| G1 | `saveTokenRecord` 的保存路径**只落三个字段**，任何传入的 `docHash` 被静默丢弃 → 续期永远拿不到素材 | `lib/token-store.mjs:72-80`（显式重建 `{token, issuedAt, expiresAt}`） |
| G2 | 全局清扫**删除所有已过期记录** → 带 `docHash` 的过期记录（= 续期输入）被当成垃圾清掉，断送「重启后续期」这一头号场景 | `lib/token-store.mjs:84-89`（`now > rec.expiresAt` 即 `delete`） |

**G2 的实际后果**：会话 B 明天签发一次 token，就会顺手扫掉会话 A 那条已过期但可续期的记录 →
A 次日再 `eng_coder` 直接落到「从未签发」。这是本批要治的场景，会**非确定性地失败**。

## §4 非功能标准（含度量方式）

| ID | 标准 | 度量方式 |
|---|---|---|
| N1 | **零新增依赖**：纯 `.mjs`、无构建步骤 | `package.json` dependencies 数不变（= 0）；`node --check` 全绿 |
| N2 | **失败不砖化**：持久化失败仅 `console.warn`，内存态继续服务 | 注入不可写 store → 仍返回新 token + 有 warn（用例） |
| N3 | **续期失败方向必须是 fail-closed**：文档不可读/缺失/歧义一律视为「已变更」并拒绝续期 | 用例：删除文档 / 改权限 / 移走 → 拒绝且不 spawn、不改 state |
| N4 | **无死代码残留**：删掉的导出面不得留空壳 | 静态断言：`advisor.mjs` 不含 `createHmac` / `TOKEN_SECRET` / `token-secret`；导出面无密钥链 6 个名字 |
| N5 | **可测试性**：全部新增行为可由 `node --test` 驱动，不依赖真实网络/真实 LLM | 新增用例数 + 全量回归绿 |
| N6 | **波及面可控**：`eng.mjs` 的 `validateDesignToken` 调用签名不变 | `eng.mjs` 仅改过期分支与文案，不改校验调用形态 |
| N7 | **磁盘格式纯追加**：不新增迁移脚本，旧记录读得动 | 读入无 `docHash` 的旧记录 → 不崩、按「无法续期」处理（用例） |

## §5 范围边界（明确不做）

1. **不改写门禁的 fail-open**（`eng.mjs:167`）。会诊中 glm 建议改 `deny`+逃生门，deepseek 论证必须保留——
   父侧采纳后者：改 deny 并不增加真实防护（`pwsh` 旁路仍在），却引入「门禁自身出错砖掉会话」的新风险。
2. **不做 `consume-design`（链终消费）**：本仓无此概念（全库零命中），不引入。
3. **不在未过期路径上校验 docHash**：那会让每次合法的文档澄清都强制重评，等于把痛点换个位置。
   代价（未过期窗口内文档漂移不被发现，窗口 1h→7d）**显式接受并记录**（见设计文档 §6 决策 **D7**）。
4. **不做公共层/提示词重构**（属批 7）；**不做轮次豁免**（批 4）；**不做上下文预算**（批 5）。
   ⚠️ **例外并属本批**：`lib/prompts/main.md:19` 的会诊生命周期口径修正（US-8 / FR-T7）——
   它是**单行口径纠正**（现行文与 `consult.mjs` D-28 实现矛盾），不是重构；
   设计评审 #7 指出其可追溯性缺口，故显式登记在此。
5. **不动 token 的「每评审会话只铸造一次、每轮同一批准码」语义**（R2 保持不变）。
