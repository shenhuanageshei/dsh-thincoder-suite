| 律 | 内容 | 对应的已发教训 |

#### §2.1 ⚠️ 父侧对三家发布门形态冲突的裁定（**关键**）

三家的形态**互相冲突**：v4-pro = 仓根脚本 · glm = **`gate-as-test`**（不建脚本，测试档即门禁）· kimi = 仓根脚本 + 七闸。

**裁定 = 仓根脚本（采 v4-pro / kimi），否决纯 `gate-as-test`。理由是时序**（父侧实跑核实）：**`gate-as-test` 结构上无法断言计数相等性。**

> `node --test` 的用例数**包含门自己这个测试档**。若把「静态计数 == CHANGELOG 顶部 N」做成套件内用例，则该用例在**测试文件写完的那一刻就被计入**，而 CHANGELOG 的计数要等**全绿之后**才写 ⇒ **自指，永远无法在单次运行内成立**。实测佐证：批 8 的套件内静态计数 413 是在 `test/prompt-contract.test.mjs` 落盘后才等于 CHANGELOG 的 `413`。
>
> ⇒ **计数相等性只能在 tag 时点断言（那时 CHANGELOG 已写定）**，不能在写测试时点断言。

**但采 glm 的一半**：**「不新增测试层」不等于「不新增测试」**。**不依赖计数的门断言仍做成常驻套件内用例**（保真、且**保证会被执行**——本仓文化已把 `node --test` 当通用门）：
- `test/` 无 `.skip` / `.only(` / `skip: true`（锁住「套件诚实」；现状即 0 命中）
- `package.json#version` 与 CHANGELOG 顶部 `## [x.y.z]` 一致（**版本**一致性与计数无关）
- CHANGELOG 顶部计数行**形态**合法（可推导式：`基线 X + 本批 Y` 或 `基线 X − 退役 Z + 新增 M = 实测`——**形态**可验，**数值**留给 tag 时点）
- 档清单等值**引用 T-E19 既有闸，不重复造**

### ④ `verify`：**取声明式门禁**，且落点**不是新工具，而是机械消费已存在的声明通道**

**语义分叉的裁定依据（含 kimi 的上游先例，父侧已实读核实）**：宿主复跑有**六条**实测代价——
1. **schema 冲突**：`check` 是**自由文本**（`validateStages` 只校验非空）。要可执行就得约束形态 ⇒ 改 `validateStages`/`renderStagesBlock` ⇒ **撞 T9 字节 fixture（基线锁）**；不约束则从自由文本提取命令 = **把模型输出当 shell 跑**的注入面。
2. **必然重复执行**：阶段纪律本已要求子代理跑过 check 才能进阶（`eng.mjs:317-318`）。
3. **dsh 同步路径上的可行性硬伤**：该路径本就在 budgetCap 墙钟内赛跑（`eng.mjs:840-845`）——塞进一次全量套件复跑（10–60s）会**把好交付变成超时 abort**。
4. **边际收益 ≈ 0**：复跑唯一多抓的是**撒谎的子代理**，而流程第 8 步（交付评审：我亲自跑测试）**已经是强制节点**。
5. **误红面**：R-13 flake 会让复跑对好交付机械转红 ⇒ **噪声训练人无视门禁**。
6. **架构先例**：上游**明言**把工程模式排除在机械完成侧守卫之外（`completion.mjs:70-74` verify 守卫 · `:118-122` advisor 守卫）——批 9 若上宿主复跑 = **逆上游自己的架构裁定**。

**落点 = `eng_coder` 返回路径上的阶段状态表机械核验**（单 helper，如 `stageGateNote(stages, outputText)`）：
- **声明通道已存在且是契约**（`eng.mjs:320`）；机械解析交付报告**已有先例**（`deliverBookkeeping` 解析 `Touched files:` 尾行）。
- 触发面：**表缺失** / **任一 `failed`** / **`skipped` 无 summary** → 在交付文本**前部加机械横幅**（响亮、点名阶段号与状态，走 `warnPrefix` N4 通道先例）。
- **五个成功交付返回点全部接入**（`eng.mjs:665/:719/:790/:918` + 同步 dsh `:920` 一带）；**失败/abort 返回点不接**（失败交付已是失败，无需声明闸）。

#### §2.2 ⚠️ 父侧对「门是否阻断簿记」的裁定（v4-pro 与 kimi 在此分歧）

| 家 | 主张 |
|---|---|
| v4-pro | 任一 stage `failed` ⇒ **跳过 `deliverBookkeeping`**（D-20 语义延伸）+ 信封标 FAILED |
| kimi | **横幅 · 不阻断**（父侧审计需要报告全文；阻断会毁掉信息） |

**父侧裁定 = kimi 的形态（横幅 · 不阻断），但吸收 v4-pro 的诊断价值**：

1. **阻断簿记是「机械推回」，与上游先例相悖**（§2-④ 第 6 条：工程模式**刻意**用 flow-driven review 而**不是** per-turn mechanical pushback）——批 9 若阻断，就是**逆上游的架构裁定**。**条形**则与先例一致（可见、不阻拦）。
2. **簿记是簿记，不是奖励**：阶段表自报 `failed` 与「交付是否发生」是**两个轴**。`mutatedThisRun` / `touched` 描述**磁盘上真实发生了什么**——子代理确实动了文件，跳过簿记会**让评审链看不见真实变更**，从而**制造更糟的静默**（正是本批要治的物种）。
3. **信息不可毁**：v4-pro 自己也写了 AC-V4「跳过簿记的交付，主代理仍能读到完整报告」——即它已意识到阻断有信息代价。父侧取**只保留收益、不引入代价**的形态。
4. **D-20 的真实教训被泛化了**：D-20 要治的是「**失败**交付销毁评审预算」。`stopReason !== completed` 时**交付未完成**（报告可能被截断，簿记确实危险）；而「completed + 阶段表自报 failed」是**已完成的交付，只是内容有缺陷** ⇒ 正确处置是**响亮标注 + 交给流程**，不是静默改簿记语义。

> **登记**：v4-pro 的「跳过簿记」形态不予采纳，理由如上，**留痕于本档**（不静默丢弃）。若将来实测出现「阶段表自报 failed 却仍被当成功交付推进」的受害案例，可重开此裁定（登记为观察位）。
