### ② 「指针 + 触发字段」的定义与落点

**三家在「值域」上收敛，在「加不加列」上分歧（父侧裁定见下）**。

**字段定义（全仓首次落定）**：
- **指针** = 权威证据的**单一引用**。词法：`<仓库相对路径>:<行号>`｜`docs/<档>.md §<n>`｜`CHANGELOG [x.y.z]`｜`—`（未定位）。
  - **只机检「文件存在」，不机检行号**——行号是位置提示不是身份，上方插入就会漂；锁行号 = **制造必然噪声**（**D-37 的教训正是「把会漂的东西锁成锚」**）。
- **触发字段** = 使该条目**被重新检视的充分条件**。值域**闭合**：`批 N`（已排期）｜`条件：<可判定谓词>`（谓词须原则上可判定，**禁散文**）｜`永不（<理由>）`（对应 §5 不吸收项）｜`—`（已闭环）。
  - 交叉不变式：`待修` ⇒ 触发 ∈ {批 N, 条件：…}（**待修却「永不」= 矛盾**）；`已修` ⇒ `—`。

**落点裁定**：

| 面 | 加不加 | 理由 |
|---|---|---|
| **缺陷登记表** | **加两列**（指针 + 触发） | 主面；现行 file:line 散在「证据」格自由文本里、触发条件写在状态格里当散文 ⇒ **确有缺口** |
| **吸收清单 §2** | **只加触发列**（指针不加） | **否决加指针列**：它的指针要指向**上游**批次档（`D:\workspace\thincoder\...`），**本地无法验存在性** ⇒ **「不可验的指针列比没有更糟」**（v4-pro）。§2 的 file:line 已内嵌在「我们现状」格，约定保留 |
| **§5 不吸收各条** | 把已有散文触发**收编为** `永不（…）/ 条件：…` 句式 | §5:126 的「待条目量或并行架构出现再评估」本就是**触发条件的散文形态** |
| **交接页 §4** | **不加列**，只成文化一条约定：引用登记表条目**只用 ID** | 刻意人眼闸；指针与触发的**家都在登记表**，交接页不复制 |
| **docs/README** | **不动** | 「文档」列的链接**本身就是指针**；文档无触发语义 |
| **test-lifecycle §三** | **不动** | 它**已是本批要推广的现成范本**（档名列 = 行键即指针；判据列 = 退役触发）——设计档点名此渊源 |

**「没指针的行怎么办」= 状态-字段耦合律**：`已定位` ⇒ 指针必填（无则降级为 `待定位`）；`待修/待排` ⇒ 触发必填；`已修` ⇒ 指针 = CHANGELOG 版本锚。

### ④ D-31：取**报错**，不取回显

**三家一致。父侧采纳，且严重度按 §1-7 上调。**

- **报错形态**：未知顶层键从 `notes` **移入 `errors`** ⇒ `ok:false` ⇒ **HTTP 400** ⇒ **不写盘**。消息镜像**嵌套分支的既有形态**（`"engineering" is not a supported top-level field (user-layer whitelist: …)`）。
- **决定性理由 1（一致性）**：**嵌套未知键今天就是报错**（§1-8，三处测试在案）⇒ 顶层是全函数**唯一的例外分支**。D-31 的修复**不是引入新严格性，而是恢复函数自身的一致性**。
- **决定性理由 2（严重度上调）**：参见 §1-7——报错方案在 `:682` 就返回，**同时消灭「静默清空整个 user 层配置」这条数据丢失路径**。回显方案（200 + dropped 列表）**保留该路径**。单此一条，报错胜出无悬念。
- **回显被否决**：回显只能把「静默丢」变「响亮丢」——字段照样不落盘、且因整体替换从磁盘消失。D-31 的伤害是「**丢 + 报成功**」，回显只治后一半。
- **D-31 唯一的顾虑（客户端 ⊆ 服务端白名单，否则设置页死锁）用一条新锁消除**：断言 `draftToPayload` 能产出的全部顶层键 **⊆** `topAllowed`；两侧**都从源码字面解析**（测试读两文件字节，**不手写清单**），含「解析器今天确实解析出 ≥N 键」的自证段。任一侧将来加键忘同步 ⇒ 红。
- **U3c（基线档断言）的处置**：走 **`AP_TEST_AUTHORIZED` 授权通道**（批 9 对 `codex-runner.test.mjs` 的 D1 先例已证此通道可用；数组所在档**非**基线档 ⇒ 改它不触发锚 B）。U3c 改写为「unknown → `errors` 非空、`ok:false`、`sanitized` 不含」。**反证实验**：摘除登记行 ⇒ T-AP9 红（唯一）⇒ 还原。
- **`saveUserConfig` 整体替换语义不改**：报错后未知键在**校验层**即被 400 拦下，**磁盘永不接触它**，「被丢键从磁盘消失」的路径已封死；改 merge 反而引入「如何显式删键」的新语义面（full-state PUT 下「删除」正是靠**缺席**表达），**为不存在的问题扩面**。

### ⑤ D-36：**不构成削弱**，但它**是对既有裁定 D1 的明示推翻** ⇒ 必须照推翻办

**三家一致「不削弱」，父侧采纳，并采 kimi 的「旧案」要求。**

**三层论证**：
1. **信任边界层**：盘记录由本插件自己签发时写入；能伪造 `design-tokens.json` 的攻击者已坐拥 `$DSH_HOME`（可改会话文件乃至插件本体）⇒ **盘与内存在本威胁模型内权威等价**。令牌的职能是**工作流门禁**（强制「先评审后写码」），**不是**防本地攻击者的密码学屏障（D-30 删密钥链时已定此调）。
2. **纪律不变式层**：门禁要守的谓词是「**本会话**有过一次通过的设计评审且未过期」。盘记录按 sessionId 索引——**重启是会话恢复（同 sessionId），不是新会话**；新会话/分叉无记录，门禁照样拒。**内存被重启抹掉，不改变「评审已通过」这个事实**。更力：`state.mjs:11-13` 解释 token 不进 session-state 的理由正是「**双盘写 = 双事实源**」⇒ **D-30 本就指定 token-store 为持久事实源**（过期+docHash 记录留 30 天的清扫规则**正是为重启后可查证而设计**）⇒ **门禁不消费它才是与设计意图的偏差；本修复是完成 D-30，不是削弱 D-30**。
3. **★能力边界层（v4-pro 的决定性证据）**：`eng.mjs:516-521` 的**回填路径已经在**——主代理在 danger-full-access 下本来就能读盘上 token、带原值调 `eng_coder`、触发回填、打开门禁，**只多一次子代理往返**。⇒ **内存态在重启后对主代理不构成能力边界，只构成摩擦**（这正是 D-36 登记的痛）。补「门禁自己读盘」**不创造任何新能力，只缩短已存在的等价路径**。

**★代价（唯一真正的代价，必须正面处理）**：D1 收窄防的是「盘 token 经 eng_coder **静默**驻留 state、**间接**打开主门禁」。本修复让门禁**自己显式读盘**——**终态相同，但路径从静默间接变为显式直接**。**推翻理由成立**：D1 护的是「不经持票人同意的隐式提升」，而门禁显式读盘是经过本批设计评审与用户批准的**明示语义**；且配上日志留痕，**可审计性反而高于现状**（现状的摩擦会诱导「为小修付一整轮评审」的变通，**变相激励绕过纪律**）。
⇒ **设计档必须设「推翻 D1」专节**（载旧裁定原文 + 推翻理由 + 「显式 + 留痕」如何回应 D1 的原始关切），且 **`eng.mjs:518-519` 的注释同步改写**（注释与新行为矛盾 = doc-code drift，交付评审必查）。**否则下一轮分歧审计会把本修复当回归抓出来。**

**六个条件（不加放宽，恰是这些条件使它不是放宽）**：
- **a** 仅 `state.designToken` 为空时读盘；读法 = 复用 `loadTokenRecord`（含其 fail-safe：文件缺失/损坏 → null → **按无记录拒绝**，**绝不 fail-open**）——**注意这与门禁 `:264-265` 自身故障放行的 catch 不同层：读盘失败 ≠ 门禁故障**。
- **b** 判据与内存路径**完全同构**（`validateDesignToken` = 形状 + 过期）：过期盘记录 → 拒 + 文案同 expired 分支。
- **c** sessionId 精确匹配。
- **d** 放行时落**一行可见日志**（`gate: design token restored from token-store (session …, expires …)`）——把 D1 反对的「静默」改成「留痕」。
- **e** 回填入 `state`（避免每次写操作重复读盘）但**必须带日志**；撤销路径零变更（§1-12 的同流程双清 ⇒ 撤销语义自动保持）。
- **f** **内存路径逐字不动**；**docHash 不进门禁判据**——今天内存路径也不查 docHash，盘路径查反而造成**两路径判据不一**（那才是真放宽/真收紧的不一致）。docHash 的现职是续期与审计。**「文档被改后令牌是否应失效」是另一个命题**，若要做须**两路径同做、另立批次**——本批**明示排除**并写进设计档「已知边界」，**防下批误认为遗漏**。
