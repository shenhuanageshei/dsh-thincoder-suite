## §4 教训（**主代理写**）

1. **「按行号改」不等于「按口径改」**。设计评审 #6 只点名 README 的两个行号，实施就只改了两行——同一口径在 `lib/` 还有 5 处**用户可见**文案（含哨兵告警正文与模型读的工具描述）没跟。**下一批起：凡「口径类」修订，任务书必须写「先全仓 grep 该口径，再逐处判读现役/历史」，而不是给行号。**
2. **抬基线会连带改变「支持面表述」的语义**。`SUPPORT_FLOOR_HINT` 一直用 `PLATFORM_VERSION_BASELINE` 拼「只支持 ≥ X」，在基线与 peer 同值时不暴露；一抬基线就变成了错误的支持承诺。**下一批起：任何基线段变更，必须同批审「所有拼接该常量的句子在语义上还对不对」。**
3. **接受标准也要能变红**。AC-10 是**假腿**（把它盯的那行 note 放在一个修与不修都不会出现的分支里）——这与本批立项要治的物种同源。设计评审没抓到，会诊 4 家里 1 家抓到。**教训：写 AC 时必须先回答「它在什么情况下会红」，答不上来就不该写进去。**
4. **并发窗口内的「快照」要标时间**。glm 读到的是实施前/父侧修复前的工作区，因此报了 3 条已被修掉的「残留」。**结论要按读到的时间点判读**，不能当成互斥证据。
