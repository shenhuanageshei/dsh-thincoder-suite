让评审结论从「宿主猜散文」变成「评审员给确定性信号，宿主机械判定」——

## §2 背景与问题

### §2.0 D-33（本批实测根因，2026-09-12 现场复现）

**工程流程被卡死，且完全静默。** 批 3 的第二轮设计评审回了 PASS，但随后 `eng_coder` 拒绝执行，
报「从未签发」；令牌存储里**没有本会话的任何记录**。父侧实测定位：

| # | 观测（父侧实测） | 结论 |
|---|---|---|
| 1 | 通过词表实测只有三个词：`通过` / `批准` / `approved`（`lib/advisor.mjs:735`） | **根因** —— 评审员的通过表述「**无未决 🔴、无新增阻塞项，可交 eng_coder 实施**」一个词都没命中 |
| 2 | 文本内词表命中数 = **0**（`通过`=0、`批准`=0；唯一的 `approved` 出现在评审员复述指令的 `not approved` 里，被当**否定语境**跳过） | 判定为不通过 |
| 3 | `verdictPassed = completed && isApprovalVerdict(result)` → `true && false = false` | 签发条件为假 |
| 4 | `lib/advisor.mjs:1588` 整条 if 为假 → `:1589`/`:1594` 未执行 | state 与 store 均无令牌，eng_coder 报「从未签发」 |
| 5 | `:1617-1628` 因 `completed` 为真而**撤销**（无「本轮是否曾签发」判别） | **连历史记录一起清掉** —— 会诊独立提出的第三个缺陷（D-34） |
| 6 | `:1631-1639` 的诊断**只在 `verdictPassed` 为真时**追加 | **失败完全静默** —— 用户只看到「从未签发」，看不到真因 |

**⚠️ 一处重要修正（父侧自查）**：我最初把本条描述为「**中文**评审被误判」—— **不准确**。
精确说法是「**通过表达的措辞未命中三词词表**」：实测 `isApprovalVerdict("I approve this design.")` 与
`"Approval granted."` 同样返回 `false`。修正后的表述直接决定修法（见 §5 边界第 1 条的 D-h 取舍）。

**为什么会这样**：`isApprovalVerdict`（`lib/advisor.mjs:741`）的通过词表是三个固定词；
核对其 20+ 条断言（`test/advisor-config.test.mjs:391-433`）可见 —— **通过态样本全部使用同一句
`"The design is approved with no unresolved Critical issues."`**（夹具常量 `:841`），
故「措辞稍有不同」这一整类情形**从未被测过**。

**这条根因改变了本批的定位**：VERDICT 不是「让结论更好读」的便利改进，而是
**修一个会阻断工程流程、且静默的缺陷**（P5/P6），并顺带修一个**会销毁有效令牌**的过宽撤销（P7）。

### §2.1 四件事各有其痛

| # | 现象 | 根因（已核验） |
|---|---|---|
| 1 | 裁决表会把「已派工但没修完」写成「已修」——**表格在撒谎** | Action 词表只有三值（`Fixed` / `Not an issue` / `Deferred`），无法表达在途；四处复制：`lib/prompts/discipline.md:4`、`lib/prompts/engineering.md:217`、`lib/index.mjs:790`、`README.md:51` |
| 2 | 宿主判断「评审过没过」靠**正则猜散文**；猜错即卡死（见 §2.0） | `lib/advisor.mjs:741` `isApprovalVerdict`，带**三版踩坑记录**（`:732-738`）与 **20+ 条边界断言**（`test/advisor-config.test.mjs:391-433`），且**通过态样本全英文** |
| 3 | 评审员「什么问题该算多严重」全凭发挥 | 无固定判据；上游 thincoder 有 **R1–R7e 共 11 条**（R1–R6 六条 + R7a–R7e 五条；实测来源：`thincoder/src/prompts/advisor-round1.md` 的 Judgment Rules 段） |
| 4 | 判定失败**不可见** | `lib/advisor.mjs:1631-1639`：诊断只在 `verdictPassed` 为真时追加；为假时**什么都不说** |

### §2.2 一处比「猜测」更严重的问题（会诊勘察纠正，父侧已核验）

**我方给评审员的说明书里有一句不成立的承诺。**

`lib/prompts/advisor-round1.md:25` 告诉评审员：代码明显非代码变更时回一句 all-clear，
**「宿主通过 'all clear' / 'no 🔴' / 'review passed' / 'no issues found' 这些标记识别它」**。

**但宿主根本没有解析代码评审的结果。** 父侧核验：

- `isApprovalVerdict` 全库**只有一处调用**（`lib/advisor.mjs:1582-1587` 的 finalize 谓词块——**设计期**是同一处单行 `:1463`；批 3 落地后该块内共 3 处调用），在 `reviewType === "design"` 分支内（`:1572`）；
- `reviewType` 在 `lib/advisor.mjs` 全库只出现一次，且是**作用域校验**（`:1477` `if (reviewType !== "design" && !paths && !documents)`），不是结果判定。

即：**代码评审的通过与否，宿主完全不管** —— 那行说明书是一句假话。
VERDICT 落地后这句话才第一次成真。这不是「加个格式」，是**把假话改成真话**。

## §3 功能用户故事

| ID | 用户故事 |
|---|---|
| US-1 | 作为**评审的发起者**，我想要裁决表能如实表达「已派工、还没修完」，以便我不必靠追问才知道真实进度 |
| US-2 | 作为**同一个发起者**，我想要评审结论是一个我能直接读的明确信号，以便我不必去猜评审员那段散文到底算过还是没过 |
| US-3 | 作为**宿主**（插件），我想要在评审员给出明确信号时**机械判定**、没给时按老办法回落，以便行为不会比现在更差、只会更准 |
| US-4 | 作为**评审员**，我想要一套固定的判据（什么算严重、什么不该卡人），以便我的判定可预期、不被反复质疑 |
| US-5 | 作为**发起者**，我想要「文档里前后说法不一致」这类发现**不要卡住通过**，以便评审聚焦在真问题上 |
| US-6 | 作为**维护者**，我想要提示词与解析器**不能各自漂移**，以便将来改一边时另一边不会悄悄失效 |
| US-7 | 作为**发起者**，我想要代码评审也有明确结论信号（而不只是给评审员看的空承诺），以便主代理不必自行揣测 |
| US-8 | 作为**发起者**，我想要评审判定失败时**看到真因**（而不是只被告知「从未签发」），以便我知道该重跑评审还是该查别的（**D-33 实测痛**） |
| US-9 | 作为**发起者**，我想要评审员**用中文表达通过时不被误判为不通过**，以便中文会话不会静默卡死工程流程（**D-33 实测痛**） |

| ID | 标准 | 度量方式 |
|---|---|---|
| N1 | **行为不倒退**：没有 VERDICT 行时，判定结果与今日**逐字节等价** | 既有 T16 的 20+ 条 `isApprovalVerdict` 断言**原样全绿**（不改断言） |
| N2 | **失败方向正确**：除「通过 + 有效回显」外的一切分支**绝不签发** token | 负向用例逐分支断言（含截断、畸形、双行、错位） |
| N3 | **提示词与解析器不可漂移** | 静态断言：四份 advisor 提示词含契约字面串；解析器与提示词同批改动由用例互锁 |
| N4 | **零新增依赖 / 零构建** | `package.json` dependencies 仍为空（AC-28 既有断言保持绿） |
| N5 | **可测试性**：全部新行为由 `node --test` 驱动，不依赖真实 LLM | 新增用例数 + 全量回归绿 |
| N6 | **误拒成本最小化**：宽松容忍（加粗/尾句号/大小写/CRLF）不得造成漏判 | 容忍面逐项有用例；放宽项不得放宽到接受多行或错误值 |
| N7 | **判定失败必须可见**（D-33）：任何导致「评审员说通过但未签发」的路径都要给出**可区分**的诊断 | 逐路径断言诊断文案；静默即视为不达标 |
| N8 | **中文会话不被误判**（D-33）：中文表达通过时，判定结果为「通过」或「回落取到通过」 | 用**本次实测的真实评审文本**作为夹具断言判定为通过（防回归） |

## §5 范围边界（明确不做）

1. **不删启发式**（用户裁定）：`isApprovalVerdict` 保留为**回落路径**，行为不变。理由是它已由 20+ 断言锁定，删掉会让无 VERDICT 的回复失去判定。

   > ⚠️ **D-33 的边界（本批的关键取舍）**：既然实测证明它在中文通过语上判错，为什么不直接**扩充它的词表**？
   > **因为那是错的修法** —— 词表扩充是同样的字符串匹配问题的延续（这次漏「无未决 🔴、可交 eng_coder 实施」，
   > 下次漏别的），且会让 20+ 断言继续膨胀。**正解是让评审员给出不依赖语气的显式信号（VERDICT）**，
   > 启发式退回真正的「回落」角色。本批因此**不改其词表**，只改**谁优先**与**失败可见**。
   > 这条取舍必须写进设计档的决策记录（含被否决的「扩词表」备选）。
2. **不在本批给代码评审建宿主门禁**（决策 D-d）：代码评审只拿**提示词契约**；宿主侧门禁属批 6（评审链守卫）。
3. **不做公共层重构**（批 8）；**不做轮次豁免与三振护栏**（批 4）；**不做上下文预算**（批 5）。
4. **不引入除 PASS/FAIL 之外的第三个值**：`CHANGES-REQUIRED` 被否决（连字符/下划线变体风险；且「🔴 即阻塞」已是既有严重度语言）。
5. **不做本地化变体**：VERDICT 关键字**永不翻译**（评审员被要求用会话语言回复，故提示词必须显式说明该 token 不译）——与既有 `[APPROVE:<code>]` 同款纪律。
