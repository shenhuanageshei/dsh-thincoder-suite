## 一、三层判据（按**处置政策**定义，不按测试风格）

| 层 | 判据 | 处置 |
|---|---|---|
| **① 批次脚手架锁** | 锁的是**易变施工事实**：行数 / 档数 / 批次号 / 当批特定文案句 / 内部中间形状（含指纹常量） | 批次收口**默认退役**（需 R1–R4 之一成立；本批退役 0 档） |
| **② 插件行为契约** | 锁**对外可感行为**：配置合并 / HTTP API / stage 渲染 / 提示词契约 / 守卫不变式 | **常驻**（`standing`）+ 发布门 |
| **③ 实况事故收编** | 由**真实死亡 / 复现事件**补入（`death-provenance.test.mjs` 整档即此形态） | 常驻，**最高保留优先级** |

- 「大小 / 年龄 / 久未失败」**明确不是**退役判据（§二 R1–R4 的封闭清单为准）。
- 层由**处置政策**判定；一个档可同时具有多层性质，此时 `层` 单元格写作 `①+②` 形态，并以**处置**为准。
- taxonomy **住在本台账，不住在文件系统**：不建 `test/integration/` 目录实体（建目录会撞 T-E19 登记制与 T-AP9 基线锁）。

## 二、退役判据 R0–R4（每条**必须举证**）与反 tautological 四律

### R0（排除项 —— 防自毁，**一票否决**）

**元锁档**（`death-provenance.test.mjs` / `guard-e.test.mjs`）在其锁存活期间**不可退役**。

> 理由：删除它们 = 删除锁本身，**套件照样全绿而锁已消失**。这是唯一能「安静地」拆掉整个锁体系的路径。
> 机验：`test/test-lifecycle.test.mjs` 断言 R0 档名**不得**出现在退役日志行；交付评审把「元锁档出现在任何 diff 的 D 列」列为**一票否决**。

### R1–R4（退役判据，**全部须举证**）

| 判据 | 定义 | 举证要求 |
|---|---|---|
| **R1 死契约** | 被锁行为已不存在（功能移除 / 重设计） | 引用**移除它的 commit sha**（该 sha 必须存在，且 `git show` 证实它确实删除了所述档/用例） |
| **R2 衰变锁 / tautological** | 断言**无法转红** | **变异实验证明**：破坏被保护物 → 该用例**仍绿** = 实证（附实验命令与两跑结果） |
| **R3 被取代的重复** | 另一测试**严格更优**地锁同一契约 | **点名取代者测试 id**（档名 + 用例标题逐字） |
| **R4 环境代理断言** | 锁的是**作者机器属性**而非仓库属性（批 8 `AC-9b` 的 CRLF 教训） | **环境无关性反证**（在与作者机器配置不同的环境上复跑的结果） |

### 反 tautological 四律（凡是锁都必须满足；交付评审必查）

| 律 | 内容 | 对应的已发教训 |
|---|---|---|
| **律 1 谓词写全** | 锚的通过条件必须精确命名其**域**（历史 vs 工作树 vs 基线集合）· **何谓改**（新增 / 修改 / 删除分开）· **自指**（锚所在文件是否在集合内） | D-37 两次返工 |
| **律 2 独立事实源** | 锚断言的必须是**测试档自身之外**的事实（git 历史 / 命令输出 / 他档字节） | 批 7 `AC-P13` 静态锁 tautological |
| **律 3 还原即红（强制变异矩阵）** | 每条保护性断言的交付报告**必须**含「破坏被保护物 → 目标用例红且不误伤」的实验记录 | 批 4/7/8 已实践，本批升为 AC |
| **律 4 锚不动** | 基线用**固定 sha / 常量**，**禁止** HEAD 相对锚 | D-37 的原罪 |

**递归终止点**：元锁（T-AP9 / T-E19）锚的是 **git 历史——不可变，故不衰变**，递归在此闭合。

### fail-open 自白（批 9 分歧审计 F5 —— 登记既存取舍，**行为零改动**）

**事实**：台账-历史一致闸（`test/test-lifecycle.test.mjs`）在**无 git**（或基线 sha 不可解析）时，把下列断言**降级为 `console.warn`**，整体仍报 **PASS**：

| # | 降级面 | 触发条件 |
|---|---|---|
| ① | T-LC4 的**基线集合等值**（10 档字面常量 == `git ls-tree <BASELINE_SHA> -- test`）——并**连带跳过**同分支内的**第四方子集谓词**及其三条合成行自证 | `gitRead(["ls-tree", …, BASELINE_SHA, …]) === null` |
| ② | T-LC5 的变异 **(2)**（sha 存在但未发生所述删除）与 **(4)** 的 `git rev-parse HEAD` 前置 | `gitRead(["rev-parse","HEAD"]) === null` |
| ③ | T-LC5 的 **(6) 事实底座**「git 全史 `test/` 零删除」 | 同上 |

**不降级**（无 git 也照常断言）：T-LC1 / T-LC2 / T-LC6（纯 fs + 字面常量）· T-LC3 的 R0 两问 · T-LC4 的 `AP_BASELINE_SHA` 字面锚（读源码字节，不调 git）· T-LC5 的 (1)(3)(5)。

**为何选降级而非强红**：该闸约一半期望值来自 git。强红会让**整个套件**在**无 git 的导出环境**（zip 解包目录 / 非仓库工作树）**无法运行**——把「元锁」变成「套件不可用」，代价远大于收益。

**代价（明说，不许淡化）**：在无 git 环境下，**「台账 ↔ 基线集合」这条腿事实上未受检**；该环境的全绿**不得**被当作「基线未漂移」的证据——须另用带 git 的复跑取证。
