## §2 问题（本批次收口阶段暴露的三个真问题）

### 问题 1：插件曾整体不可用（已修复，两个独立缺陷）

**现象**：`advisor` / `eng_coder` / `consult` / `contractWatch` 等 11 个工具全部 `unknown tool`，但**客户端设置页能渲染**（报 `config API 不可用：Failed to execute 'json' on 'Response': Unexpected end of JSON input`）。

**根因（两条，互不相关，均带实证）**：

| # | 根因 | 证据 | 修法 |
|---|---|---|---|
| ① | `profiles/desktop/package.json` 声明了 **3 个盘上不存在的 bundle**（`@deepseek-ai/dsh-experimental-agent-team-profile` / `-auto-review` / `-schedule-bundle`）⇒ loader 解析失败**中止整棵 profile 树** | `dsh --profile desktop --dump-config` 报 `Error: dsh: cannot resolve profile bundle "…"` ，栈顶 `loadProfile` | 从 39 条删到 36 条（备份 `package.json.bak-deadbundles-20261015-175106`） |
| ② | `apply` 里读 `ctx.goals` 但 `goals` 未在 `inject` 声明 ⇒ cordis **白名单**直接抛 `Error: cannot get property "goals" without inject` ⇒ **apply 中断、11 个工具全未注册**（模块本身已 import，故极易误判为"没装载"） | 临时探针实测（`[apply ENTER]` → `[apply THREW] …`） | 改为 `ctx.get("goals")`（该读法**不需要 inject 声明**）+ try/catch 兜底（`lib/anti-drift.mjs:1130`） |

**关键教训（写给后来者）**：**「模块被 import」≠「apply 被调用」**。本批次在这个坑上耗费了大量轮次——因为客户端包被静态服务（所以"页面能渲染"），而服务端 `apply` 早已抛错退出。判定"插件是否真的挂上"必须以**工具可调用**为准，不能以"客户端页面能开"或"工具目录里有名字"为准。

### 问题 2：v4 会话格式的 content 槽事故（真机，另一会话在热修）

**现象**：会话**再也打不开**（`dsh://session/<id>` 打开即空、再发消息无反应），而盘上文件**结构完好**（zstd 帧与 JSON 行全部合法 ⇒ **容器级体检报 ok**）。

**根因**：本插件把 `agent.inject` / `agent.steer` 的 `content` 传成**裸字符串**，而 session format v4 要求**数组**。写盘层的检查器是「**有则检查、无则放过**」（`assertContent` 的 `if (Array.isArray(content))` **没有 else**）⇒ 裸串**静默穿过写盘**、当场不抛；只有**读取/播种层**才硬性要求数组（`assertMessageEventShape`：`if (!Array.isArray(messageRecord["content"])) throw`）。

**影响面（真机全库扫描 1677 个会话）**：**仅 3 个**会话含非规范 content（2 阻塞 + 1 潜伏），且**全部来源都是本插件的两条注入路径** —— 即本插件是**全库唯一来源**。

**状态**：另一会话已在工作树上实现修复（`producerContent(text) → [{type:"text", text}]`），**尚未提交**。接手者**不要覆盖它**。
