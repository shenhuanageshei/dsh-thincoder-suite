## §1 总目标（一句话）

让本插件的**产品提示词不再绑定任何具体仓库**：评审的判据来源由**项目自己声明**（缺省时显式降级而非静默），提示词里不再出现本仓/上游的文件名与路径，且「这个路径是文档还是代码」这件事**只有一个权威实现**。

## §2 背景与问题

| # | 问题 | 根因 | 证据（as-of 批 6b 交付后实测） |
|---|---|---|---|
| **P1** | **`METHODOLOGY.md` 写死在产品提示词** | 插件把「项目标准」硬编码成某个**具体文件名**，并整段注入 | `lib/**` 共 **19 处**命中：`advisor-msgs.mjs` 8 处（含 `:212-222` 整段注入器）· `prompts/advisor-design.md` 2 处 · `prompts/engineering.md` **9 处** |
| **P2** | **注入器静默失效（今日恒不生效）** | `injectDocumentMap` 读 `resolve(cwd,"docs","design","README.md")`——**本仓无 `docs/design/`**，地图在 `docs/README.md` | 实测两处路径**均不存在**；`lib/**` 内该文件**零消费点**。**缺陷物种 = 写死路径 + 静默 catch**：它坏了几个月没人知道 |
| **P3** | **上游悬空名被当成本仓文件指涉** | `engineering.md:198` 枚举 `(design doc, METHODOLOGY.md, ENGINEERING-MODE.md)`——后者**本仓根本不存在** | 根目录实测无该文件 |
| **P4** | **判据两份矛盾副本** | 「这个路径是文档还是代码」被实现了两遍，各有盲区 | `eng.mjs:48` `isProductCode` vs `advisor.mjs:1671` `isDocFile`。形式化：`isProductCode = ¬D∧(S∨¬E)`、`isDocFile = D∨E` ⇒ 唯一矛盾类 `¬D∧S∧E` |
| **P5** | **`^src/` 锚是死代码，却制造唯一矛盾** | `^src/` 快路径在扩展名判定**之前**返回 | 对代码扩展名冗余（兜底已覆盖 `lib/`、`packages/app/src/`）；对文档扩展名短路 ⇒ `src/README.md` 门禁拦、评审却接受 |
| **P6** | **锚定短路自相矛盾** | 同一逻辑位置因嵌套深度不同结果相反 | `src/README.md` 被拦，`packages/app/src/README.md` 不被拦 |
| **P7** | **退役会造出新的静默洞** | 若只删注入器不改注入门：已声明却被 `engineering` 模式静默压制 | `injectMethology` 今日挂在 `if (!engineering) return` 上 |

**P2 的方法论价值**：它是本批要消灭的**缺陷物种的活标本**——「写死一个具体路径 + 静默 catch」的组合会让功能死掉而无人察觉。故本批的声明键机制**必须带显式降级句**（J4），而不是又一个静默 catch。

## §3 功能用户故事

| # | 用户故事 | 判定句（可机验） |
|---|---|---|
| **US-1** | 作为**插件作者**，我希望产品提示词里不再出现任何**具体仓库的文件名/路径**，这样插件装到别的仓也能用 | `grep -ri "methodology" lib/` = **0** 命中；`grep -rn "docs/design" lib/` = 0；`grep -rn "ENGINEERING-MODE" lib/` = 0 |
| **US-2** | 作为**项目**，我希望**自己声明**哪个文件是我们的标准，`standardsDoc` 指向它就被注入进评审上下文 | 设置 `advisor.standardsDoc` → 评审上下文出现 `## Project Standards` 段 + 该文件全文；提示词只说「若上下文有该段则据其评判」 |
| **US-3** | 作为**排障的我**，未声明时我希望**看见它没声明**（而不是猜为什么评审没按我们的标准来） | 未声明 ⇒ 上下文出现**显式降级句**（逐字可断言）；**声明了但读不到** ⇒ **与未声明可区分**的响亮句并点名该配置键 |
| **US-4** | 作为**评审员**，声明了标准却被 `engineering` 模式静默压制这种事**不该发生** | 注入门 = **声明键存在**，与 `engineering` 标志无关（J7）；已声明 ⇒ 必注入 |
| **US-5** | 作为**评审员**，标尺太长时我不该收到一个被悄悄截断的判据 | 超 16384 字符 ⇒ 截断 + **带标记**（对齐 `PROJECT_GUIDE_BUDGET` 先例） |
| **US-6** | 作为**架构师**，我希望「这是文档吗」只有一个答案——今天同一个路径在写门禁和评审校验里可能得到相反结论 | 新建 `lib/path-kind.mjs` 为**唯一**权威；两处消费均为其派生；`src/README.md` 不再自相矛盾 |
| **US-7** | 作为**维护者**，我希望修 `^src/` 时**不要把门禁收紧**（上游那个动作是陷阱） | `lib/`、`packages/app/src/`、`test/` 下的代码文件**仍判产品代码**（真阳性不丢）；`^src/` 字面在 `lib/` 内零命中 |
| **US-8** | 作为**用户**，我希望在**设置页**就能填标准文档路径，并看见当前生效值与来源 | 设置页出现文本框；`fieldSource` 显示「全局覆盖 / 内置默认」；改完 PUT 落盘 |
| **US-9** | 作为**本仓**（dogfood），我希望退役后**不丢失**现有的 methodology 注入 | 本仓经**配置**声明 `standardsDoc = "METHODOLOGY.md"`（部署注记）；该配置在则注入照旧 |

## §5 边界与登记面

### §5.1 本批不做

| # | 不做项 | 理由 |
|---|---|---|
| 1 | **不做仓内声明文件**（`.thincoder/review.json` 等） | 它在工程模式下**写自己就需要令牌**；为它开门禁豁免 = 引入**人工维护的例外清单**（吸收清单 §4-9 的教训：必漂移）。改用插件配置键：**零门禁交互**、且是可移植的正确层 |
| 2 | **不做会话级覆盖** | J10：`standardsDoc` 是**项目属性**，与 `contextTokens` 同族（全局唯一） |
| 3 | **不改 `docs/` 的归属** | 代码文件落进 `docs/` 属**布局违规**，由评审与分歧审计抓；堵它需要「代码扩展名清单」（人工清单必漂移） |
| 4 | **不修** 六维/七维清单漂移 | R-5 登记（本批只换措辞不并维） |
| 5 | **不动** `.thincoder/advisor.md` 读取链 | R-6 登记 |
| 6 | **不动** `viz/*.html` · `METHODOLOGY.md` 本体 · `docs/**` 历史档 | 退役范围**只**是产品提示词面 |
